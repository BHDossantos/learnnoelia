## Fixed behavior

- Direct student writes could previously forge attempt status, published scores and response grades under permissive `FOR ALL` policies. Migration `0051` revokes direct attempt/response mutations and replaces start, autosave, score and publish writes with narrow, authenticated RPCs. Only the service role can submit server-computed grades. Answer keys remain teacher/server-only.
- Submission previously ignored response/attempt/gradebook errors and performed separate commits. Server grading now checks every read and requires valid question keys, then calls a transaction that locks the attempt and writes its responses, score, gradebook and mastery evidence together. Persistence failure leaves the attempt open and retryable. Written attempts remain submitted until every written answer receives an explicit teacher score, including zero for skipped answers.
- The submit form includes the full latest answer snapshot, including answers whose debounce timers have not fired. Autosaves are queued in browser order, report failures, and take the same database lock as final submission. A late autosave fails after submission instead of changing graded answers.
- Question/key mutations lock the assessment and are rejected once it has attempts. Start takes that lock too, keeping the server's grading inputs stable. Parent deletion cascades remain supported. To change a question or key after attempts exist, create a new assessment.
- Teacher score changes require the exact classroom, attempt and written question, a submitted/unpublished attempt, a bounded score and an existing response row. Missing rows cannot return success. Grading controls are disabled for published attempts. Publication is also blocked while any written score/feedback is dirty or saving; score inputs are locked during save and publication. Explicit async busy state is used because React 18 transitions do not await async callbacks.
- Publication commits all result stores together. Repeat submit/publish calls are idempotent. One unique formal mastery event per attempt/question prevents repetition from inflating mastery. A single successful answer yields proficiency, never sustained mastery. The existing `skill_states` constraint omitted the `assessment` kind and is corrected. Formal mastery events/states cannot be modified through student self-study policies.
- Published assessment attempts are immutable through this grading flow. A proper versioned correction/regrade workflow is still required; the old “re-publish” behavior silently inflated evidence and is intentionally removed.
- Latest default already has `0047_grade_item_assessment.sql`. The **unapplied** tutoring migration initially moved to `0048`, then to `0050_tutor_settlement_integrity.sql` after concurrent default added `0048_assessment_expansion.sql`. After upstream added `0049_assessment_monitoring.sql`, assessment integrity moved to `0051`; tests and documentation use the final unique sequence. Do not rename migration history on a database that has already applied a conflicting version; reconcile that environment first.

## Validation and limits

SQL regressions execute migrations `0030`, `0046`, upstream `0048`/`0049` and the actual new `0051` in PGlite, with minimal profile/classroom/gradebook fixtures and authentication helpers. They cover forged writes, key secrecy, outsider access, definition freezing, final-snapshot precedence, late autosave rejection, transaction rollback, repeat publication, evidence protection, missing written rows and parent deletion. Action tests cover missing/failed reads, malformed answers, persistence failures and missing-row scoring failures. Four React component regressions exercise unsaved/pending/failed score saves and publication locking with deferred server-action promises; these are not browser E2E tests. Concurrent Promise calls are serialized by PGlite; these are **not** multi-connection PostgreSQL race tests.
